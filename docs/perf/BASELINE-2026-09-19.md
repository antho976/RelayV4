# Relay performance baseline — 2026-09-19

The first full measurement of the engine: every one of the 210 bus ops, the 36 paths that are
not ops, the process at rest and under load, memory over time, and the CLI. Numbers are from
`runs/2026-09-19/` (raw JSON, and `report.md` with every table); this document reads them,
says where each cost goes, and whether it is the work or overhead that can be cut. The next
baseline is compared against this one with `scripts/perf/compare.py`.

In one paragraph: the engine is cheap where it matters most. A keystroke is 16 µs in process
and 96 µs through the socket; the session list the shell reruns on every change is 39 µs; six
live sessions cost **zero** CPU and zero wakeups at rest; memory is flat over 20 000 operations.
The expensive paths are the ones that touch git or the filesystem, and most of those are the
work itself (a checkout is a checkout). Eight things stand out as overhead rather than work,
ranked below; the first three are worth doing soon because they run under the store mutex and
stall every other request while they run. (Seven of the eight were fixed the next day; the
before-and-after numbers are in `FIXES-2026-09-20.md`.)

## 1. What is worth fixing, in order

Each item: what it costs, where the cost goes, why, and what to do. "Where it goes" is from
callgrind (instructions, deterministic: self cost by subsystem, and the inclusive share of named
functions) and from strace (syscalls); the times are native. The full breakdown of every
scenario is in `runs/2026-09-19/report.md` under "Where the instructions go".

### 1.1 `overlap.flag` and `overlap.scan` hash every file of every session worktree, under the store mutex

- **Cost:** 31 ms wall and **74 ms CPU** per call with two session worktrees (it is
  multi-threaded); 21 600 allocations, 12 MiB, 18 800 syscalls, 105 M instructions. In a dry run
  where earlier cases had left thirty abandoned worktrees the same call took **1.5 s at 260 %
  CPU**. Linear in open sessions × files per checkout.
- **Where it goes:** gix is 56 % inclusive and the hottest self entries are `sha1_checked`
  (about a third of all instructions) and `memset` (18 %): the status walk in `changed_files`
  is *content-hashing every file* in each worktree, not comparing stat data, because a fresh
  checkout's index carries no stat cache that gix trusts. A further 10 % is `sha2`: the symbol
  hashes `changed_symbols` computes with tree-sitter. `scan_project` itself is 15 %. Both
  handlers use `Engine::register`, so all of it runs inside the transaction with the store mutex
  held; `overlap.flag` runs the whole scan as a side effect of recording one flag.
- **Why it matters:** the invariant `CLAUDE.md` names — anything slow under the mutex blocks
  every other request. Keystrokes themselves are exempt (D148 keeps `session.input` off the
  store, and a keystroke issued during a scan measured 55 µs), but the session list the shell
  refreshes and the scrollback tail it reads are not: both measured 35 ms while a scan ran. An
  agent flagging a path stalls every terminal's display for 30 ms, or for seconds with a busy
  wall. Fixed on 2026-09-20; see `FIXES-2026-09-20.md`.
- **Fix:** move the walk into the read phase of `Engine::register_staged` (the shape
  `session.create` already uses for its checkout), so only the row writes hold the lock; record
  the flag without rescanning; run the status with stat-only comparison (refresh the index
  stat cache once after checkout, then trust it) so unchanged files are not rehashed; cache the
  per-worktree result keyed on the index mtime. Expected: the flag becomes a ~300 µs write, the
  scan stops blocking the bus, and a rescan of an unchanged wall costs a stat walk (about
  10 ms for 1 500 files, on a worker).

### 1.2 `task.list` compiles SQL for every task row

- **Cost:** 2.42 ms for 40 tasks, 22.7 ms for 400 (9.4×, linear), 60 µs per task, 17.3 M
  instructions; on the socket 3.4 ms and 28.9 ms. It is the board's load and the query the Board
  page reruns on every task event.
- **Where it goes:** SQLite is 70 % of the instructions and **61 % is `sqlite3_prepare`**, the
  SQL compiler, against 11 % executing; the hottest self entries are `sqlite3RunParser` and
  `yy_reduce`. `row_task` (`handlers/task.rs`) is 81 % inclusive: it hydrates each task with
  seven sub-queries, and five of them (labels, three relation edges, children, plus the rollup
  walk) use `tx.prepare` rather than `prepare_cached`, so 40 tasks compile ~240 statements per
  call. The list statement itself is built dynamically and prepared uncached too. JSON is 8 %.
- **Fix:** `prepare_cached` on every per-row statement, and cache the built list statement by
  its filter shape (a dozen combinations). Then fold the per-task queries into three batch
  queries over the id set, which removes the per-row round trips. Expected: 2.4 ms → well
  under 1 ms for 40 tasks, and the per-task cost drops from 60 µs to the row itself. The same
  hydration is 71–86 % of `module.get` (2.9 ms, 65 % compile), 57 % of `dashboard.get`
  (1.1 ms, 46 % compile) and behind `module.changelog.draft` (2.6 ms → 25 ms at ×10); they
  improve with it.

### 1.3 The merged flag on every branch is a fresh merge-base walk with no object cache

- **Cost:** `git.branch.clean_merged` (dry run): **520 ms, 619 ms CPU, 143 500 allocations,
  545 MB allocated** for a 3 KB answer. `git.branches`, which computes the same flags, was
  10 ms with 13 300 allocations earlier in the same run, and 0.6 ms on a fresh fixture. The
  difference is history: between the two measurements the fixture gained ~60 commits on `main`
  and ~30 branches.
- **Where it goes:** `branches_for` is 73 % inclusive; the self cost is `zlib` inflate (27 %),
  `memset` (14 %) and allocation (12 %), and the instruction count is small (11 M) against the
  CPU time, which says the time is page faults on 545 MB of freshly zeroed buffers, not
  computation. For each branch, `repo.merge_base(head, branch)` walks from HEAD back to the
  branch point decompressing each commit anew: cost is **branches × distance to the base**,
  with every commit inflated once per branch because no object cache is shared across the
  calls. On a real repository (thousands of commits, dozens of branches, a base that is far
  behind old branches) this is the branch list on the Code page taking seconds.
- **Fix:** one reverse walk from `HEAD` marking reachable commits (what `git branch --merged`
  does), then each branch's flag is a set lookup; turn on gix's object cache
  (`repo.object_cache_size`) for the walk. Expected: milliseconds regardless of branch count,
  and a few hundred KB.

### 1.4 `device.build` dirty-checks every worktree before finding there is no Gradle wrapper

- **Cost:** 133 ms, 23 ms CPU, 26 100 allocations, 17 400 syscalls of which 10 000 are
  `newfstatat`, to return `device.gradle_missing`. Under the mutex.
- **Where it goes:** `resolve_run_root` → `worktree::list_with_dirty` is **92 % of the
  instructions**: to validate the requested root it lists the project's worktrees and runs a
  dirty check on each, and a dirty check is a `git status --porcelain` subprocess
  (`status_files`, 29 %) plus a gix open. Only then does `build_command` look for `gradlew`.
  The stats are git's. On a machine with the SDK the same preamble precedes a real build, where
  it is a smaller share but still ~130 ms of blocked bus.
- **Fix:** test for the wrapper first; validate the root without the dirty check (§1.6); take
  the pre-build inspection out of the transaction (`register_staged`). Expected: the refusal
  becomes microseconds; the real build path stops blocking the bus during its preamble.

### 1.5 Engine startup is crash recovery, and crash recovery scans `/proc` and dirty-checks every worktree

- **Cost:** `path.engine.startup` is 161 ms on a populated store, of which `recovery::run` is
  157 ms; 20 300 syscalls, 10 400 of them `newfstatat`; 39 500 allocations, 17.8 M
  instructions. A real restart is 32–37 ms clean but **1.5 s** after a kill with six live
  sessions.
- **Where it goes:** `pty::relay_children` is **55 % of recovery's instructions**: it reads
  `/proc/<pid>/environ` for every process on the machine (`proc_env` 46 %, and 9 % is the
  lossy UTF-8 conversion of those environments) looking for `RELAY_SESSION`. On this container
  that is about a hundred processes; a desktop has several hundred. `worktree::list_with_dirty`
  is 20 %: it opens every project repository and runs a `git status` subprocess on every
  worktree, which is the 10 000 stats and most of the wall time (157 ms wall against 39 ms CPU:
  the rest is git and the subprocess poll backoff). In the full startup, recovery is 62 % of
  the instructions and `skills::refresh_all` 18 %. After a kill, `kill_wait` on the surviving
  child is the extra ~1.3 s.
- **Fix:** record the pids the engine spawned in the store and check those directly rather
  than scanning `/proc`; run the dirty-worktree flagging on a worker after the socket is up (it
  is advisory). Expected: startup on a populated store under 20 ms with the socket answering
  before any walk.

### 1.6 Every project-scoped file and git op re-validates its root by enumerating worktrees, and `file.tree` pays a full status for badges

- **Cost:** `file.tree` at depth 1 is 11.2 ms (10 KB result); `git.status` 11.3 ms;
  `git.branches` 10 ms; `worktree.list` 17.6 ms for two checkouts; the status walk alone is
  10.6 ms.
- **Where it goes:** `status_files` is a **`git status --porcelain` subprocess**
  (`proc::output_with_timeout` is 91 % of its instructions; 10.6 ms wall against 1.5 ms CPU is
  git's own walk plus the poll backoff). In `file.tree`, `root_verify` → `worktree::contains`
  is 35 % of the instructions and `status_badges` (that subprocess) 20 %; in `git.status`,
  `resolve_root_unlocked` → `worktree::contains` is 25 % and `upstream_metrics` (another git
  subprocess, for ahead/behind) 16 %; in `git.branches` root validation is 30 % and
  `upstream_metrics` 21 %. `worktree::contains` opens the repository with gix and enumerates
  its worktrees on every call to check that the requested path is one of them. So a one-level
  tree listing is two gix opens and one git process, on every folder expansion.
- **Fix:** validate the root against the store's own worktree rows (it knows every checkout it
  made) and canonicalize once; memoize the status per worktree keyed on the index mtime and
  the watcher's last event (the watcher already exists: `watch::ensure_after_commit` runs on
  every tree call); compute ahead/behind through gix rather than a subprocess. Expected: tree
  listings and status drop from ~11 ms to well under 1 ms between changes; `worktree.list`
  likewise.

### 1.7 Plain `file.search` builds a substring searcher per line

- **Cost:** 60 ms (80 ms CPU, 102 M instructions) for a query with no hits over 1 500 files:
  40 µs per file, 21 000 allocations, 18 100 syscalls. The regex form of a different query
  stopped at its 100-hit limit after fewer files, so its 22 ms is not comparable; per
  instruction it is the cheaper path.
- **Where it goes:** `core::str::pattern::StrSearcher::new` is **20 % of all instructions**:
  `line.find(&query)` constructs a two-way searcher for every line of every file; `memchr`
  13 %, the loop itself 21 %, `memcmp` 5 %. Files are read with `read_to_end` into a reused
  buffer, which probes in chunks (7 100 `read` calls for 1 500 files, 4.8 per file).
- **Fix:** build one `memchr::memmem::Finder` for the query and search the whole buffer,
  mapping hit offsets back to lines; size the read from the file's length so it is one call.
  Expected: plain search at a few milliseconds for 1 500 files.

### 1.8 `session.spawn` renders the brief and materializes skills every time; `session.list` looks columns up by name

- **Cost:** `session.spawn` 22.7 ms with 15.8 ms CPU and 1.3 MB allocated (`session.wake` the
  same); `session.brief` 704 µs and 622 KB for a 3.6 KB answer; `skill.create/update/enable`
  2–7 ms at p95 with 3–4 ms CPU. `session.list` is 39 µs, which is fine, but 11 % of it is
  `sqlite3_column_name`.
- **Where it goes:** `session::launch` is 92 % of spawn: `awareness::brief` 34 % (of which
  `git::briefing_state` 24 %, gix upstream metrics for the brief's git lines), `Pty::spawn`
  20 %, `skills::materialize` 14 %, guardrail setup 12 %. `session.brief` is `briefing_state`
  55 % and `divergence` 25 %: it re-derives ahead/behind from the object store each time (zlib
  inflate shows in its self cost). Each skill mutation re-materializes into every checkout
  (`skills::refresh_all` is 34 % of `skill.create`). In `session.list`, `sessions::row` reads
  every column by name, and rusqlite's name lookup (`sqlite3_column_name` + `strlen` per
  column) is the top self entry.
- **Fix:** small. Cache the brief's git lines per (worktree, HEAD, upstream tip); materialize
  skills only into checkouts whose enabled set changed; read columns by index in
  `sessions::row`. Expected: spawn CPU roughly halves; brief reads become a lookup;
  `session.list` loses ~15 %. Low priority: none of it runs on a hot path.

### Not overhead, but worth knowing

- **`session.create` 264 ms (p95 408 ms):** a `git fetch` against the origin plus
  `git worktree add` of 1 500 files, run unlocked in the staged read phase; 63 % of its 7 M
  instructions are gix (`list_with_dirty` after the add, to find the new checkout) and the wall
  time is the git subprocess. `worktree.create` runs the same command and measured 635 ms; the
  gap is unexplained by this run (same syscall count, same work) and worth a look, though
  nothing in the shell calls `worktree.create` on a hot path.
- **`project.clone` 263 ms (p95 694 ms):** a full clone of the 1 500-file repository; the
  work.
- **`git.commit` 29 ms, `git.fetch` 26 ms, `git.push` 36 ms:** subprocesses; the work, and
  unlocked so they do not block keystrokes. `git.branch.delete` 19 ms with 17 ms CPU and
  1.9 MB is on the high side for deleting a ref: it runs `branches_for` afterwards (§1.3).
- **`git.show` 7.4 ms, 91 M instructions, 5.2 MB:** the commit shown added the 1 MiB fixture
  file, and `git::counts` (77 %) diffs it line by line with `similar` to report added and
  removed counts; hashing 26 %, the diff 22 %. Proportional to the diff; the work.
- **`session.close` 36 ms, `session.park` 10.5 ms:** the park is almost all waiting (0.5 ms
  CPU): the SIGTERM grace bounded by how fast `sh` exits. The close adds `worktree::remove`
  (15 % of instructions, and the `git worktree remove` subprocess is most of the wall) and
  `dir_size_all` (14 %: it walks the checkout to report the MB freed) plus hook uninstalls.
  The grace period runs inside the transaction when the worktree is being removed; a provider
  that ignores SIGTERM holds the bus for the full 150 ms.
- **`task.activity` 2.6 ms, 4.6 M instructions:** `audit::get` 27 % and 25 % JSON; the top
  self entry is SQLite's `jsonTranslateTextToBlob`, so the audit query is parsing JSON payload
  text inside SQLite per row. Storing the payload as JSONB (SQLite ≥ 3.45) would remove that.
  1.4 ms in the clean ×10 fixture; it scales with the task's audit rows.
- **`bus.whoami` 409 µs:** `guardrail::write_roots` is 40 % (it canonicalizes each root:
  27 `statx`, 15 `readlink`) and gix 33 %; cheap enough for a call agents make once.
- **`bus.schema` (whole) 9.7 ms, 160 KB; `bus.ops` 1.0 ms, 60 KB:** rendered from the
  registry on each call; clients call `bus.ops` once at connect.
- **`session.scrollback` with no line limit: 3.4 ms and 10 MB allocated** to return the whole
  1.8 MB ring as JSON. The tail form is 17 µs. The shell uses the tail form.
- **`app.backup.now` 2.9 ms; `provider.refresh` 3.5 ms (four subprocesses); `Engine::new`
  9.8 ms (99 % is the 19 migrations on an in-memory store, tests only):** the work.
- **`settings.set` 185 µs:** `settings::get` is 62 % of it (the tree is read back to merge)
  and the audit row 13 %; SQL execute 66 %, compile 34 %. Expected for an audited write.

## 3. The engine at rest, and under output

A real `relay serve` with six fake sessions, sampled from `/proc` over 30-second windows.

| phase | CPU | wakeups/s | RSS |
|---|---:|---:|---:|
| six quiet sessions | **0.0 %** (0 ms in 30 s) | 0.0 | 22.0 MiB |
| same, resources panel watching | 0.033 % (10 ms) | 1.2 | 22.2 MiB |
| six sessions printing 10 lines/s each, nobody attached | 0.13 % (40 ms) | 67 | 22.3 MiB |
| same, a client attached to all six | 0.53 % (160 ms) | 178 | 23.0 MiB |

**Idle is genuinely idle.** Zero CPU ticks and zero context switches in thirty seconds with six
live PTYs: no timer, no poll, nothing wakes. That is the strongest number in this document and
the one to protect. The resources panel costs one wakeup a second and a third of a millisecond of
CPU per second while it is open, which is its sampler; fine.

**Output costs 22 µs a line to absorb and 89 µs a line to forward.** 1 800 lines in the
unattached window cost 40 ms: the PTY read, the ring append, the broadcast to nobody. With a
client attached the same lines cost 160 ms, so 120 ms of that is the socket side: a frame
encoded to base64 and JSON, written, and the client's own reads. 67 wakeups a second unattached
is one per line (sixty lines a second plus the samplers); 178 attached is one per line for the
reader thread plus one per frame for the writer. These are all expected for the design, and small:
a wall of six chatty agents keeps the engine under 1 % of one core.

**A burst does not reach a slow client whole.** One session printing 50 000 lines (4.9 MB) in
one go: the engine spent 140 ms of CPU on it (28 ms per MB through the ring and the frame
encoder), and the attached client received 2 414 frames carrying 1.19 MB of the 4.9 MB. The
stream is bounded by design (a lagging subscriber is dropped rather than allowed to stall the
engine, and the scrollback ring holds the whole burst for a re-attach), so this is not a loss
in the engine; it is what an attached reader that cannot keep up sees. The native client
re-attaches from its last sequence with a bounded 256 KiB catch-up, so a burst larger than
that shows a gap in the terminal rather than every line. Whether that gap is visible in VTE is
a client question the client script is meant to answer.

**Restart.** A clean start on a fresh store answers its first ping in 28 ms; a clean restart on
this store in 32–37 ms. A restart after the engine was killed with six sessions alive took
**1.5 s**: recovery found one child still alive and reaped it (the others had already died
with their PTY), and `kill_wait` is where the second went. The in-process measurement of the
same path on a copy of the store without live pids is 156 ms, so the reaping is about 1.3 s
of the 1.5 and the rest is recovery's own walk, discussed under engine lifecycle below.

**Memory.** RSS is 15.7 MiB before any session and 22.0 MiB with six. Over 20 000 mixed
operations the live heap went from 2.62 MiB to 2.83 MiB, and 170 KiB of that 210 KiB arrived in
the first 2 000 operations (statement caches, buffers reaching their working size); the last
18 000 added 38 KiB, which is the audit log's in-memory side. RSS grew 24 → 32 MiB in the same
run while the store file grew 0.6 → 4.5 MiB, so the RSS growth is SQLite's page cache following
a growing database, not a leak. Nothing here needs attention.

**CLI.** `relay ping` from a cold process is 3.8 ms at the median (3.6 minimum): process start,
socket connect, one round trip, exit. `relay q session.list` is 4.4 ms. Every hook Relay
installs into a provider pays this once per invocation; it is small and dominated by process
creation, which Relay does not control.
## 4. How this was measured

Everything below comes from one run of `scripts/perf/baseline.py` on 2026-09-19 against
commit `842daf3` (`main` after PR #14), in the dev profile that `run.sh` launches. The raw
JSON and the generated tables are in `runs/2026-09-19/`; `runs/2026-09-19/report.md` has every
scenario, and this document reads them.

The machine was a four-core Xeon container at 2.8 GHz with no display and no Android SDK, so:

- absolute times are that machine's, and a desktop with a faster core and an NVMe disk will be
  quicker in wall time by some constant. Ratios between scenarios, the instruction counts and the
  breakdowns carry over;
- `device.*`, `avd.*`, `github.*` and `skill.install` were measured on their refusal path (no
  adb, no emulator, no `gh`, no network). That is the cost the engine pays to say no, which is
  still worth knowing, but it is not the cost of a build or a mirror;
- the GTK client could not be built here (GTK 4.14 against the 4.22 pin, see `CLAUDE.md`), so
  the client half of this baseline is a script, `scripts/perf/native-baseline.py`, and a section
  at the end saying what it will measure. Nothing in this document is a client number.

The harness measures each scenario four ways, on one disposable fixture: a 1 500 file
repository with a bare origin, a store on disk with 40 tasks, 5 modules, 10 notes, 10 messages
and 3 skills, two live PTY sessions (a builder and a paired reviewer running a shell script that
answers like a provider), one open guardrail hold. Every case that creates rows undoes them
outside the measured region, so the store a case sees is the fixture and not what the cases
before it left behind; the `rows` field in the JSON records the live counts at each measurement.

| pass | what it gives | how |
|---|---|---|
| native | wall p50/p95, process CPU, allocations, bytes, result size | 200 / 30 / 6 iterations by expected cost, after warm-up |
| ×10 rows | the list queries against 400 tasks, 100 notes, 100 messages | a second fixture built with `--scale 10` |
| callgrind | instructions per iteration, self cost by subsystem, inclusive cost of known entry points | instrumentation switched on only around the measured call, one dump per scenario |
| strace | syscalls per iteration, every thread | strace attached for the loop, harness clock reads excluded |
| soak | live heap and RSS over 20 000 mixed ops | allocator wrapper counting live bytes |
| process | idle CPU and wakeups, output streaming, restart, CLI startup | a real `relay serve`, sampled from `/proc` |

## 5. What is not in here

- Anything the GTK client does: paint, layout, VTE, GtkSourceView, icon and CSS cost, frame
  timing. That is the client script's job, on a machine with GTK 4.22.
- Real providers. The fixture provider is a shell script; a real `claude` or `codex` process
  costs what it costs, and Relay does not pay it.
- Network. `git.fetch` and `git.push` went to a bare repository on the same disk.
- The success path of Android tooling, GitHub and skill installation.
- Long-running behaviour beyond the 20 000-op soak and the thirty-second process windows.

## 6. The client half

`scripts/perf/native-baseline.py` opens the real window against a disposable engine with six
fake sessions, once per page (`agents`, `board`, `code`, `notes`, `modules`, `plan`, `settings`,
`skills`, `dashboard`, `notifications`, `devices`, the launch preview, the palette, the layout
menu), then once more on `agents` with all six terminals printing ten lines a second, and once
with the smoke harness's 2 048-line burst into every pane. For each it records:

- CPU spent in the first two seconds (process start, engine connect, first paint, navigation),
  and RSS at that point;
- CPU percent, wakeups per second, RSS and thread count while sitting on the page;
- with `perf` installed, a sampling profile of the client folded by shared object (GTK, pango,
  cairo, VTE, GtkSourceView, the client itself, the allocator) and by symbol, which is the
  "where does the CPU go" breakdown for the client;
- GTK's own frame log (`GDK_DEBUG=frames`) beside it, when the GTK build emits one.

It writes `runs/<date>/native/native.json` and a Markdown summary, and is written to keep going
when one page's environment variable has drifted, since it could not be run here. The
questions it is meant to answer, with the same shape as the engine sections above: how much
CPU does opening each page cost, what does the window cost while idle, what does a busy
terminal wall cost, and how much of that is Relay's own code against GTK's.
